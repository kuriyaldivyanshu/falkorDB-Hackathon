An agent that remembers what matters, not just what was said.

The challenge asks for agents that remember across sessions, share state with each other, keep memory updated over time and stay separated per user or tenant. Each of those five words maps to a concrete mechanism in this plan — section 07 and section 09 show exactly which one.
The problem

Long coding sessions lose their memory

Ask any agent user what happened after a two-hour session and they will usually say something like: "I think I told it to use the old serializer, or the new one, or maybe neither."

FAILURE 01

Context gets compacted away

The model starts summarising its own conversation to fit the window. Requirements, decisions and half-finished reasoning quietly fall out of the summary.

Like a scribe who, running out of parchment, starts paraphrasing the previous pages instead of copying them — and the paraphrase is never checked against the original.
FAILURE 02

A new session starts from nothing

Close the terminal, or hit a context limit and start fresh. The agent is now a stranger to your project. You have to re-explain the goal, the constraints and which approaches already failed.

A new shift starts on the factory floor with no handover sheet. They re-run the experiment that burned down the line last night.
FAILURE 03

Nobody can prove anything is finished

The agent says "tests pass". No one — including the agent — knows which code it ran, which version of the requirements was in force, or whether the check itself could be edited by the code under test.

A student marks their own exam and returns it. Passing is entirely a claim, not a measurement.
FAILURE 04

Two workers, duplicated work

Run a second agent to speed things up and now both edit the same files, disagree about the plan, and each holds a private copy of the conversation.

Two chefs working the same kitchen with separate notebooks and no shared whiteboard on the wall.
FAILURE 05

Private context leaks

Material from a private repository, a colleague's chat, or a paid-source document ends up inside a shared summary because the summariser was not told what it may repeat.

The new hire is summarising the private acquisition memo to the whole company because "the summary is only an internal note".
FAILURE 06

Requirements move, evidence does not

You change a requirement after work has started. Old test results stay on the wall, green, referencing a world that no longer exists.

The blueprint changed twice; the inspection certificate on the wall is still for the old blueprint and nobody re-checked it.
Most "agent memory" products today store a transcript. Recall of a transcript tells you what someone said. What a coding agent actually needs is to know what is still true — which requirement is current, which approach was tried and failed, which evidence still applies to the code as it exists right now. That is a different data problem, and it is a graph problem.

The one promise

If you only remember one thing from this document

The demo is a single continuous story. Everything in the architecture exists to make one nine-minute sequence work without a human writing a single recap paragraph.

The acceptance sentence

Change a requirement. Interrupt the Builder. Bring up a genuinely fresh successor with no memory of the old conversation. It must finish the job, and its Verifier must produce receipts that are valid only for the current requirement and the exact code that exists right now.

Interrupt a junior engineer mid-task, give them a handover sheet that says exactly what is still required, what was already tried and failed, and which requirement text is now in force — with no access to the old conversation. Then have an inspector who was not allowed near the source code confirm the work. That is the whole product.

Why "genuinely fresh" is the hard part

It is easy to fake continuity by replaying the previous conversation into the new session. That proves nothing — the model already had the information. The honest test is that the successor starts with an empty conversation and receives only a context packet that the graph assembled from current, authoritative sources. Everything it knows, it learned from the memory store, not from a transcript.

✓What Threadline does
  • New agent session, empty conversation, new write fence.
  • Context packet built from current goal/constraint versions only.
  • Failed attempts included — with their source file and digest — so the work is not repeated.
  • Old receipts are visible but marked stale; they cannot complete the task.
  • Old worktree quarantined before the successor is given write access.
✕What would be a fake
  • Replaying the previous transcript into the new session.
  • Summarising the old chat by hand and pasting it as "context".
  • Letting the Builder declare its own work complete.
  • Letting the Builder also run the final check it defines.
  • Accepting yesterday's green test after today's requirement change.
The complete architecture describes a much larger system. The hackathon release implements one bounded typed-tool loop, one explicit API provider profile, two role workers and one authored demonstration repository. Native subscription adapters, child agent spawning and extra providers are explicitly post-hackathon milestones with their own gates — not quietly half-built features.

The four trust boundaries

Every claim about safety in this document rests on these four walls. Each one is a place where one component is not allowed to speak for another.

BOUNDARY 1

Human → local service

A secret file protected by the operating system creates your user, your tenant and an expiring application session. Loopback traffic is still authenticated. A profile name typed by the model is not an identity.

BOUNDARY 2

Service → databases

Only the backend has credentials. Graph keys are derived from authorised project records — never from anything the model produced. SQL membership is checked before a query runs, not after it returns.

BOUNDARY 3

Service → runtime

Workers start with an explicit executable, workspace, allowlisted environment and a scoped tool grant. Everything the runtime emits is treated as untrusted observation until verified.

BOUNDARY 4

Service → evidence

Artifacts are content-addressed per tenant and project. Access is re-checked on every read and every citation resolution. Provider secrets never enter the graph, SQL, logs, sandboxes or prompts.

A graph-level "fence" cannot stop a shell command that is already running. Locking files in the database is bookkeeping; real containment comes from the operating system's sandbox and process isolation. The plan treats those as two separate problems and requires both.
How it works

The agent loop, one step at a time

This is the entire execution model. There is no magic agent framework underneath — just this cycle, repeated, with every step written down before it happens.

The whole thing is a ledger with a decision-maker in the middle. Before the agent is allowed to touch anything, it writes down what it intends to do. After it acts, it writes down what actually happened. The database is always more truthful than the conversation. If the two disagree, the database wins.

Why the ordering is not negotiable

Notice that step 6 — persist the full requested tool batch — happens before step 8 — execute. This is the single most important ordering decision in the whole system.

WRONG ORDER

Execute, then hope you can log it

If the process crashes between the tool running and its result being written, the system has performed a side effect nobody recorded. On restart it cannot tell whether the command ran. Retrying might double-apply it.

You mail the payment, then write it in the ledger. A crash in between and the money is gone but the books say it was never sent — so you send it again.
THREADLINE ORDER

Record intent, act, then record outcome

Intent is durable first. After the act, outcome and evidence are stored. A crash in the middle leaves an explicit unknown state — which the reconciliation pass resolves by inspecting the real repository and process state, never by guessing.

You write "payment sent, awaiting confirmation" in the ledger, then send it. A crash leaves an open question with an owner, and the reconciliation clerk checks the bank statement rather than re-sending.
MVP responsibilities

Builder and trusted checker

One logical model session at a time, inside the backend. Commands are isolated executions; the checker is a trusted service, not a second AI agent.

Builder
  • Holds the current write claim and fence.
  • Uses eleven bounded tools to inspect, edit, run, retrieve and checkpoint.
  • Requests completion; cannot declare accepted proof.
  • A fresh successor starts with an empty conversation after retirement/reconciliation.
Protected checker
  • Runs immutable inputs against exact candidate bytes in a restricted container.
  • Assertions and receipt writer remain outside candidate execution.
  • Binds service actor, check run, environment and current criteria.
  • A model Verifier is a deferred target role.
The core idea

Three kinds of memory, and what makes them different

This is the heart of Track 2. The distinction is not academic — each kind needs different rules about who can write it, how it changes and who may read it.

Episodic — the unedited record

Every tool call, its arguments, its result and its exit status, stored immutably and linked to the exact file bytes involved. The model may label an episode or point at it, but it can never rewrite what happened.

Think of a security camera. You can annotate the footage — you cannot edit it.

An example episode

Action
workspace.apply_patch on src/serializer.ts
Expected digest
sha256:9f2c… — file had to be unchanged first
Outcome
Tests failed: DateRoundTripTest lost timezone offset
Stored as
Attempt + Observation + immutable output object
Later value
A successor reads it and does not retry naive local-time serialisation
This is the single mechanism that makes the demo land. The failing attempt is not in the successor's conversation — the successor never had that conversation. It is in the graph, and the graph deliberately surfaced it as an applicable failure.

Semantic — versioned truth

Goals, constraints and decisions exist as a stable identity plus an append-only chain of versions. At any moment exactly one version is current. When the human changes the requirement, a new version is created that supersedes the old one — the old text is kept, inspectable forever, but it stops governing.

A contract with amendments. Clause 4 was replaced by Clause 4A. The signed original is still in the file cabinet, but nobody argues from it any more.

Watch the chain change

Click a version to make it current. Old receipts immediately become stale.

If a task needs a rule and the system cannot find exactly one current version of it — missing, duplicated or not visible to this worker — the agent turn is blocked. It does not guess, and it does not quietly drop the rule.

Procedural — the reusable recipe

A named, versioned recipe: the steps, their preconditions, the evidence that proved them once, and later outcomes when they are reused. A procedure is not trusted because its author was confident or because it succeeded once. It is trusted because a held-out compatible task reused it successfully.

A recipe in a test kitchen. It earns a place on the shelf only when a different dish, cooked by someone else, comes out right using it.

Visibility is a first-class property

Every memory record carries one of three visibility scopes. This is not a UI toggle — it is checked before retrieval, before citation and before publication.

SCOPE 01

project

Everyone in the project can read it. This is the default for requirements, decisions and shared findings.

SCOPE 02

user

One person. Records the owning user id. Cannot be surfaced to another member even inside the same project.

SCOPE 03

session

Access is limited to the originating agent session. Retention policy determines lifetime; private observations remain scoped. Hidden model reasoning is excluded from product storage.

If a session reads a private source, everything that session produces stays at least that private — a paraphrase of a private document is still private. Promotion to shared requires an explicit, reviewed Publication record with redaction of both the content and revealing metadata such as titles and file names.
If a source's access is revoked, every session that loaded it is retired and a brand-new sanitized session is started. But bytes already handed to a model provider or a running process cannot be recalled. The honest claim is "future access is prevented", never "the data was erased from the model".

What actually gets sent to the model

Before every turn, the system assembles a context packet: a bounded, hash-stamped document containing exactly the current governing requirements, the relevant episodes, decisions and procedures, and nothing the worker may not see.

Priority and summarization: what a successor receives

Priority follows the current task and evidence, not the tool or file type. Store captured permitted originals; select a smaller packet with source links.

  • P0 — mandatory: exact current goals, constraints, criteria, candidate identity and unresolved effects or clarification.
  • P1 — working context: the current blocker, checkpoint/checklist, relevant change excerpts, active decisions and actual failed checks.
  • P2 — conditional recollection: compatible earlier attempts, validated procedures and source-supported lessons.
  • P3 — bulk trace: verbose or repeated output and routine reads; usually referenced or omitted.

A log can be P3 while its exact blocking error is P1 or mandatory. Keep the reproduction command, actual outcome, affected candidate and source together. File names alone do not prove a change. Hidden thinking is excluded; short visible decision rationale can be useful.

Preserve authoritative requirements and critical status exactly. Use deterministic structured summaries first for optional history, keeping original source IDs, uncertainty, versions and visibility. A summary does not prove that an error was fixed.

Use one current memory block per reconstructed request. Deduplicate repeated sources, cap retrieval and recent history, and check the complete input budget as well as the 6,000-token default / 8,000-token maximum memory packet. Mandatory overflow stops inference. Retention is separate from forwarding priority.

Read the full proposed priority, representation and retention policy.

When do we save or summarize?

No separate summarizing API is required. Core uses deterministic fields/excerpts and the main agent’s ordinary checkpoint. Model-generated condensation is optional and disabled by default.

Save human input and model-request intent before dispatch; save the complete visible tool batch before effects; capture tool outcomes before dependent work. Stream logs in bounded chunks. Checkpoint meaningful failures, decisions, candidates and next-step changes. A crash uses the last checkpoint plus subsequent observations; cancellation never waits for a recap.

If optional summarization is enabled later, admit it only for meaningfully changed relevant sources at a useful phase/handoff or optional-history pressure. Reuse source/version-matching results, coalesce updates and cap calls under the existing provider/run budget. Ordinary turns do not trigger extra inference.

Read the proposed capture, checkpoint and summarization schedule.

Requirements and current criteria are mandatory — they are never dropped to save space. Optional recollections (older attempts, tangents) can be left out, and the count of what was omitted is shown. If the mandatory set alone does not fit the budget, the turn is stopped with an explicit overflow error and the user is offered a narrower task or a larger budget. Silent truncation is treated as a bug.
The hard part

Change the requirement, kill the worker, start over

Seven ordered operations. Skipping any one of them produces a successor that is confidently wrong — and that is the exact failure this whole project exists to prevent.

Requirement revision, visualised

When the human edits a requirement, the graph does three things at once, atomically: bumps the requirement revision, points CURRENT_VERSION at the new text, and marks every task holding an older revision as needing a rebase. No mass update of every task is required — the revision acts as a barrier that blocks the next action of anything stale.

Finding affected work by walking dependency edges is a nice explanation for the user, but dependencies can be incomplete. Correctness comes from a different place: every guarded action re-checks current revisions immediately before it acts. So even a missed edge in the impact walk cannot let stale work through.
Storage

Two databases, one owner for each fact

The single most common way a system like this breaks is answering the same question in two places and getting two answers. This plan refuses that: every fact has exactly one owner.

FALKORDB — the authority

Everything relational about the work

What governs this task right now. Which attempts still apply. What depends on a changed requirement. Who loaded outdated context. Whether current verification permits completion. Delete FalkorDB and those questions become unanswerable.

POSTGRESQL — the operations

Everything sequential about humans and history

Authenticating a person. Revoking a login session. Listing projects. Ordering messages. Recording what processes were observed doing. Claiming rows for delivery. Rebuilding paginated history views. SQL views are projections — they never authorise a state change.

33 tables (31 core + 2 adapter/auth extensions) · explicit migrations · tenant row-level security templates

FalkorDB is the case file. PostgreSQL is the reception log. The case file says what is true about the work: what is required, who owns it, what has been proven. The reception log says who walked in, what they said, in what order, and when. You would never keep the truth of a case in the visitor book — and you would never keep a visitor's arrival time in the case file.

How the two stores stay consistent

There is no distributed transaction across SQL, the graph, the filesystem and the model provider. Instead each crossing point has a durable protocol with an explicit recovery story.

SQL → GRAPH

Capture outbox

One SQL transaction appends the observed event, its payload and an outbox row together. A background reader publishes graph anchors using an operation ID derived deterministically from the event, so a retry finds the existing receipt instead of creating a duplicate.

Crash point: graph committed, acknowledgement lost → retry reads the original receipt. Same key with a different payload is an integrity error, not an update.

GRAPH → SQL

Event projector

The projector reads committed events strictly after its cursor and inserts them into a projection table, advancing the offset in the same SQL transaction. A missed notification causes delay, never loss. Consumers deduplicate on project, epoch, sequence and event id.

Crash point: transaction interrupted → rows and cursor roll back together and replay cleanly.

HUMAN COMMAND

Command inbox

A goal or requirement change writes the original human message and the complete immutable command envelope in one transaction, before anything is admitted to the graph. A message id plus a payload hash is not a command — the whole validated envelope is.

Why it matters: if the app crashes after the human pressed enter, the change survives and gets replayed correctly. Pending is visibly different from accepted.

MODEL CALLS

Request journal

Before dispatch, the exact permitted request bytes are stored, then a journal row binds session, logical request, attempt number, digests, epoch, revision and budget reservation. A crash at the dispatch boundary is conservatively unknown — the system assumes the call may have happened and may have been charged.

Retry is a new attempt under the same logical request, after reconciliation. Completed tool effects are never silently re-run.

There is the source position in a session, the SQL capture order, the SQL→graph admitted position, the graph→SQL projected position, and the recipient's context-inserted position. They advance at different rates and mean different things. Collapsing them is how duplicate deliveries and phantom confirmations happen.

What the graph encodes that a table cannot

WHY A GRAPH

Applicability is a question about neighbours

"Is this failed attempt still relevant?" is not a column. It is: start at the task, follow its governing constraint, find which attempts are bound to it, exclude superseded ones, and check whether any of them loaded context that is now outdated. That is a bounded traversal, not a filter.

WHY A GRAPH

Change has a blast radius

When a constraint version is superseded, the set of affected work is whatever is reachable through stable binding edges — including workers that loaded the old text and would otherwise keep acting on it. A relational design needs this as a fan-out query maintained by hand.

WHY A GRAPH

Provenance is the primary shape

Every accepted claim must be able to point back at readable source. "This decision was based on these two file versions and that failed attempt" is a traversal through the graph, checked at acceptance time, not a comment field.

Graph invariants the application must enforce

Property uniqueness alone does not give you edge cardinality, acyclicity, authorisation or valid state transitions. These are explicit contracts with failure tests behind them.

POST-HACKATHON

Two extension tables

native_bindings · provider_oauth_registrations

Kept out of core migrations on purpose. Nothing in the core release may depend on a foreign key into them.

user_sessions is a human logging into the application: a hash of a random bearer token, with expiry and revocation. agent_sessions is one logical Builder session (model Verifier is a future role). They are deliberately different entities, and neither may hold a conversation lock, a task lease, a model API key or a provider token in the wrong place.
An opaque id in a request body is only a requested target. Why TypeScript and not Rust or Python

The coordinator mostly waits — for model streams, tool processes and database replies. Then it validates events, assembles a bounded context and commits guarded changes. That is not the profile of a compute-bound program; it is the profile of an integration program.

CandidateFit for this workloadCost for this deliveryDecision
TypeScript / NodeNative protocol streams, npm packaging, React terminal UI, database I/OMust bound queues, validate input, avoid blocking the event loopSelected
RustProcess supervision, constrained helpers, CPU-heavy indexing, standalone binariesSeparate build and distribution chain, different UI ecosystem, slower iteration at this scopeAdd only after a measured need
GoStatic daemon, concurrent I/O, deployment toolingA third language that does not solve the integration problemNot selected
Rust's ownership rules would catch a real class of memory-safety bugs. They would not make a graph write and a shell command atomic, and they would not save an unobserved tool result. The risks that actually threaten this system are wrong state transitions, lost capture, stale evidence and private-source leaks — and those are solved with durable protocols, database guards and tests, not with a compiler.

Deliberately absent

No separate vector database. No Kafka, RabbitMQ or extra Redis queue. No Kubernetes. No public API gateway. No browser framework. No distributed workflow engine. No microservice fleet. No training or fine-tuning. Embeddings are optional recall sugar; exact identifiers and bounded graph traversal implement the mandatory context.

The demonstration

The nine-minute script that proves the idea

One authored repository, synthetic data, independent assertions. The feature deliberately combines a correctness bug with a freshness requirement that changes mid-flight, because that is where memory applicability actually matters.

"Can I kill the process right now and have the next agent still know what to do?" — if the answer is yes, the idea holds. Everything in the recording is arranged so that question has an answer that is demonstrated, not promised.
Two-person delivery

Functional build gates; deadline unknown

User owns Memory/Coordinator. Teammate owns Harness/Delivery. Pair on fixture, contracts and containment. No four-day commitment is assumed.

  1. Start with a small running backend and plain terminal frontend, then add real persistence and read-only model tools. Protected checker and release pinning follow the working flow.
  2. Complete one accepted goal, claim, provider/tool attempt, sourced checkpoint and receipt.
  3. Kill after durable failure capture; recover a genuinely fresh session with summarization disabled.
  4. Accept changed freshness and reject obsolete proof, without requiring an artificial code change.
  5. Create sourced candidate procedure, authorize held-out compatible trial and reject incompatible reuse.
  6. Package the tested target and execute stale/duplicate/scope/fault gates.
  7. Compare against an equivalently informed structured-checkpoint baseline.

Read the controlling contract and exact policy. Every runtime gate remains unexecuted.

Evidence

What has to be proven, and what "proved" means

Three families of deterministic cases, plus honest reporting rules. None of these has been executed yet.

Isolation tests — proving the walls hold

Two synthetic users in one project, two projects in one tenant, and two tenants with deliberately colliding display names and fabricated target ids.

What gets attacked

  • API reads and writes, graph selection, SQL references
  • Message search, source resolution, artifact access
  • Event stream replay and export contents
  • Worker enrolment with a foreign project id

What must be true

  • The application role is not owner, superuser or row-security-bypassing
  • Missing tenant context denies access outright
  • A pooled connection cannot inherit the previous request's tenant
  • Private sources inside one tenant are also protected — row-level security does not solve that case
  • Path escape, symlink escape, background process escape, environment-secret and network access all fail from a command sandbox
An allowlisted test command still runs repository code. The plan requires proving the sandbox itself — not merely that the command name matched a list.

Comparison against a plain baseline

The hackathon runs one authored scenario and one held-out recovery scenario, comparing graph memory against an equivalently informed structured-checkpoint baseline using the same provider, model, tools, source facts, acceptance bundle and aggregate budget. Every trial and every failure is reported.

Demonstration evidence, not a statistically supported quality claim. The broader campaign — five baselines, twelve predeclared variants, repeated cases within budget, published denominators — belongs after the submission. If files with equivalent closure perform equally well, the plan says to report that and frame FalkorDB's contribution around the coordination, query and operational behaviour that was actually demonstrated.

Backup and restore

Boundaries

Trust, proof and privacy

These are the sections that decide whether the project is a research toy or a tool anyone could point at real code. Each rule below exists because something specific goes wrong without it.

The verification trust boundary

A task's acceptance criteria are not "whatever npm test says today". They are a protected, content-addressed bundle that the Builder cannot modify or reach around.

WHAT IS INSIDE THE BOUNDARY
  • The assertions themselves and the runner that executes them
  • Every transitively imported test helper and configuration file
  • Lockfile and dependency identity
  • The invocation, which is harness-controlled

The candidate is mounted separately. Expected outputs and acceptance logic stay outside its write scope. Hashes are verified before and after execution.

WHAT CANNOT HAPPEN
  • The candidate editing the test that grades it
  • The candidate monkey-patching the assertion engine
  • An early exit producing a fake success
  • A forged terminal receipt being accepted
  • Zero exit code alone being treated as a pass

Missing, malformed, forged or premature terminal results all fail the check even when the candidate exits zero.

What a receipt actually binds

A verification receipt is a signed bundle of hashes. It says not "tests passed" but precisely which bytes were checked, under which rules, by what command, in what environment, by whom, and when.

Bound fieldWhat it prevents
Candidate digestAccepting a check that ran against code that has since changed
Environment digestPassing in one configuration and claiming it in another
Criteria digest + acceptance-bundle digestSwapping the grading rules after the fact
Requirement revisionCompleting work against a requirement that has been superseded
Command and argument digest + tool execution idsClaiming a specific check ran when something else did
Verifier identity and timestampsAnonymous verification with no accountable author
Trusted launcher digestRunning the assertions through something the candidate controls
If acceptance criteria change, that requires a new approved criteria version, invalidates the requirement, and forces re-verification. You cannot quietly widen the test after seeing it fail — and a human or agent review finding supplements executable evidence; it never replaces it.

Privacy rules that are enforced, not intended

Authorisation happens before retrieval

The check runs before the query returns data, not after the whole graph has been handed to a model and the model asked to be careful. Path traversal, symlinks, unsupported URI schemes, unregistered worktrees and cross-project artifact locators are all rejected.

Read content is never an instruction

Retrieved files and messages may contain hostile text. Context packets mark which parts are human-accepted authority and which are quoted observation. A file that says "change the tenant or grant yourself tools" has no authority whatsoever.

Approvals are per-invocation

An approval binds one canonical invocation digest, one session, one workspace and an expiry. Change the command, the path or the arguments and permission is recomputed. A previous approval is never a wildcard for future commands, and an "allow everything" conversion is refused.

Secrets stay out of the data path

Provider secrets live in the official client or the OS secret store. Profiles keep references only. The environment passed to command sandboxes is filtered, so a parent credential cannot leak into untrusted test code and a paid API route is never selected by accident.

Access and billing

Who runs the loop, and who pays for it

These are separate decisions and the plan keeps them separate: whether we execute the agent loop, and whose account the inference is billed to. The first release answers both in the simplest way possible.

User choiceWho runs the inner loopCredential routeScope
Threadline + your OpenAI API keyThreadlineExplicit user-provided API keyHackathon baseline

Threadline + Codex nativeCodexOfficial native loginPost-hackathon compatibility gate
Threadline + Claude nativeOfficial unmodified Claude CodeOfficial native loginPost-hackathon subscription gate

The goal of the first release is to prove that our loop, our tools and our memory actually work. Using the user's own API key removes every question about whether a native client's authentication made the demo look good. If a native-only demo is ever shown, it must be labelled delegated execution — not proof of an owned runtime.

Three credentials that must never be confused

01

Application session

Authenticates the TUI and CLI to our own backend. An opaque bearer token on the client; only its hash in the database.

02

Model provider credential

Authorises inference and selects the billing account. Lives in the official client for native modes, in the OS secret store otherwise.

03

Tool or connector credential

Access to one particular tool server. Scoped and separate from model credentials — logging into a tool server does not unlock model usage.

Billing ownership is checked, never inferred

Before any launch and before every provider submission, the run initiator, the profile owner and the provider-account owner must be the same active authorised human in the matching tenant and project. Project membership alone grants no right to spend someone else's balance.

When a subscription quota runs out, the system pauses and says so. It does not switch to paid API credentials. When usage reporting is unavailable, the answer is unknown — never zero, and never a fabricated dollar figure.

Certificate, registration and eligibility are three different things

A

The direct local route

A documented dynamic-registration flow needs no client secret and no partner API key. Its callback binds to 127.0.0.1, so no public HTTPS certificate is involved. Provider requests still use HTTPS.

B

Native clients

Threadline uses their supported control interfaces and lets the official client run its own sign-in. We do not register a replacement subscription client and we do not read their token cache.

C

Commercial or hosted use

A separate partner route. A technically successful OAuth exchange does not establish programme eligibility, and eligibility for one route never transfers to another.

OS application signing is a packaging concern. It grants no model access and no subscription usage. There is no single certificate that makes any application eligible for both providers' subscriptions.
