# Threadline development-readiness critique

**Fresh baseline review: 15 October 2026.** This reviews the current proposed architecture, including runtime sections 20–21 and the first vertical slice, before the next cleanup. It does not assume that the earlier C01–C14 findings remain unresolved. Source line numbers below describe the baseline inspected during this review; later edits can move them. The report is independent of implementation results: no runtime, database, paid provider, sandbox or recovery experiment was executed.

**Verdict:** the product direction is coherent, but the next step should be a narrower implementation contract, not another general architecture layer. The highest-value product is one coding worker that can be stopped and replaced by a genuinely fresh worker with current requirements, applicable evidence and independently checked output. The missing connections are mostly between promises and concrete producers, stored representations, selection predicates and lifecycle ordering.

The user has now clarified that there are **two full-time contributors**, not the four assumed by the existing schedules. No deadline has been supplied for this revision. Estimates must therefore be conditional on explicit integration gates rather than presented as a four-day commitment.

## 2. Detailed findings and acceptance experiments

### D01 — Freeze the workload and its authority bootstrap

**Evidence.** [Delivery §5](../track2-delivery-and-validation.md) (baseline line 65) names an inventory-export repository, serializer correctness and freshness, then asks Builder to produce a useful failed receipt and later reuse a procedure. [First slice §2](../track2-first-vertical-slice.md) (baseline line 24) promises one authored repository; [§4](../track2-first-vertical-slice.md) (baseline line 48) promises an equivalently informed comparison and held-out case. [Runtime API](../track2-runtime-and-protocols.md) (baseline line 175) admits a goal/policy, while [memory creation](../track2-final-architecture.md) (baseline line 307) correctly separates model proposals from human or scoped-policy acceptance. The bridge from the free-text goal to exact accepted constraints, criteria and the protected check bundle is not concretely selected.

**Failure scenario.** One contributor designs a JSON exporter, another interprets freshness as a cache TTL, and the verifier expects timestamp normalization. They can implement their individual interfaces while having no common executable task. Alternatively, an agent invents acceptance criteria and the coordinator silently treats them as human authority. A demonstration that requires the model to make a particular mistake can also fail because it solves the first attempt correctly.

**Minimal resolution.** Define a single authored manifest with initial repository contents or a reproducible fixture source, exact input/output examples, initial accepted rules, the one changed rule, declared commands and protected acceptance-bundle identity. Human initiation explicitly accepts that manifest/version. Treat free-form changes as pending until represented by an accepted bounded change; do not imply arbitrary natural-language-to-tests automation. Start from a deliberately imperfect authored implementation that can produce a real observed failing check, rather than requiring the model to invent a particular bad tactic. Preserve disclosure that the starting fixture is authored. Specify one compatible held-out input/task and one incompatible case. No additional model or generalized planner is needed.

**Acceptance experiment.** Before paid inference, two people independently run the same fixture specification and agree on initial failure, old-requirement pass, changed-requirement failure and final pass. The model must observe actual tool results. Both graph and structured-checkpoint comparison receive identical source facts and check definitions; neither baseline is denied information to manufacture an advantage. The package should describe itself as a demonstrated authored-workload harness until broader repositories pass.

### D02 — Connect durable capture to exact checkpoint recovery

**Evidence.** [Runtime §19](../track2-runtime-and-protocols.md) (baseline line 264) promises exact checklist artifacts/source bindings and fresh retrieval. [§21.2](../track2-runtime-and-protocols.md) (baseline line 375) promises the last durable checkpoint plus subsequent captured observations after a crash. [§20.4](../track2-runtime-and-protocols.md) (baseline line 319) requires representation/provenance metadata. However, the [TaskState fields](../schema/graph-field-dictionary.md) (baseline line 215) contain `checkpoint_text`, candidate and unresolved-effects fields without a specific structured checkpoint/checklist source pointer or covered capture position. `AgentSession.last_capture_seq` at [line 243](../schema/graph-field-dictionary.md) (baseline line 243) is the highest graph-admitted capture, not the capture covered by a particular checkpoint. [The ingester](../track2-final-architecture.md) (baseline line 198) creates anchors; [memory creation](../track2-final-architecture.md) (baseline line 307) permits model labeling without specifying how a nonzero result becomes a useful `Attempt` if the model never checkpoints.

**Failure scenario.** A test fails, its output is captured, and the worker crashes before calling `memory.checkpoint`. A successor selects the previous checkpoint but cannot identify the precise subsequent tail or a current checklist. Depending on an implementer's guess, it either misses the new failure, rereads the entire transcript, or mistakes the graph ingestion cursor for checkpoint coverage. A later checklist update can overwrite progress if both are an unspecified text field.

**Minimal resolution.** Define one immutable versioned checkpoint manifest containing progress, tactical checklist, blockers, next action, source IDs, requirement/candidate/environment bindings and explicit coverage as `(session_id, capture_seq)` pairs. A single scalar is sufficient only while its originating session is also recorded; capture sequences are not globally comparable. Store the exact manifest in existing artifacts/sources and link its identity from the current task state or another explicitly selected relation. Updating the checklist preserves the progress sections through a versioned patch/merge rule.

Define deterministic ingress for terminal command/check outcomes: stable execution ID plus actual outcome creates the observation/source and task-bound episode. A root-cause explanation remains unconfirmed unless separately evidenced. Agent-written checkpoint prose is useful, but failure capture and fresh recovery must not depend on the model deciding to write it. On recovery, reconcile unknown effects, admit any required capture tail, then select bounded post-checkpoint episodes with an explicit omitted-count/gap result. A marker that capture is ahead of the checkpoint must not be represented as a fully current summary.

**Acceptance experiment.** Kill the worker immediately after durable failed-tool capture, before any next model turn. Restart with summarization disabled and an empty conversation. The packet contains the exact relevant invocation/diagnostic and original source, the current checklist, and current authority without replaying the full chat. Repeat with duplicate outbox delivery and with checkpoint/checklist updates interleaved; one episode is admitted, coverage never moves beyond actually covered observations, and neither update loses the other section.

### D03 — Make semantic and procedural memory reachable through actual operations

**Evidence.** [Core deliverables](../track2-final-architecture.md) (baseline line 20) require episodic, semantic and procedural memory. [Procedure fields](../schema/graph-field-dictionary.md) (baseline line 408) include steps, preconditions, candidate/validated status and held-out reuse count. [Data model §4.1](../track2-data-model.md) (baseline line 82) requires held-out compatible reuse for validation. [Runtime tools/service operations](../track2-runtime-and-protocols.md) (baseline line 100) expose checkpoint, decision proposal, review and completion, but no specific procedure creation/validation transition or decision-acceptance route. [P2 selection](../track2-runtime-and-protocols.md) (baseline line 294) names validated procedures, leaving unclear how a new candidate can be selected for the held-out reuse that first validates it.

**Failure scenario.** The graph can store procedures but no service produces them, so the required demo uses manually preseeded knowledge while implying it was learned. Or a candidate never gets retrieved because only validated procedures are allowed, while validation requires a reuse that cannot start. A developer might solve this by accepting every model lesson, violating the explicit truth-promotion boundary.

**Minimal resolution.** Choose one deterministic procedure template for the authored task, instantiated from actual successful steps and a trusted receipt. Record the originating task, observed sources, exact prerequisites and `candidate` status. Permit an explicitly authorized compatible trial of a candidate as a labelled suggestion; it is not governing authority or proof. A distinct held-out task's trusted successful receipt can promote it to `validated` under a guarded service operation. Failure invalidates or narrows that version; it does not erase the original evidence. Duplicate reuse does not increment a counter twice. Default agent decisions remain `proposed`; either provide an explicit human acceptance command or omit accepted-decision claims from the MVP. This needs typed operations, not a general memory-learning agent or a new database.

**Acceptance experiment.** A clean graph contains no procedure. Complete the authored task, produce exactly one sourced candidate, reuse it on a compatible held-out task and observe the guarded validation transition. Reject the incompatible variant and stale receipt. Repeating the same receipt is idempotent. Explain in the demo what was authored as a template and what was learned from real executions.

### D04 — Remove the fresh-handoff admission ambiguity

**Evidence.** [Fresh recovery steps 5–6](../track2-final-architecture.md) (baseline line 368) create the fresh session, record packet submission/insertion acknowledgement, and then accept the handoff/claim. [Runtime loop step 1](../track2-runtime-and-protocols.md) (baseline line 11) acquires role authorization before a provider request. [Context delivery contract](../track2-runtime-and-protocols.md) (baseline line 151) binds owned-runtime insertion to `model_requests.id` and actual submitted request bytes.

**Failure scenario.** An implementation waits for a provider-submission acknowledgement before granting the claim, while the broker correctly refuses inference without that claim. Another implementation resolves the cycle by submitting a first request before authorization. A purely local packet-load acknowledgement could avoid both, but it is not distinguished from provider submission in these steps.

**Minimal resolution.** Use an explicit order: retire/quarantine the previous writer; reconcile actual workspace/effects; construct and stage the fresh packet locally; atomically accept the handoff and assign the new claim/fence under current revisions; reserve/persist/submit the first provider attempt; record its actual packet insertion evidence. A local staging record is not a provider submission. Any failure after claim acquisition leaves a recoverable claimed-but-not-submitted session, never evidence that the model received context. Preserve per-attempt submission IDs.

**Acceptance experiment.** Inject failures at packet staging, claim commit and provider dispatch. No request reaches the provider before valid role authority, no effect occurs before the first applicable submitted context, and recovery distinguishes no-send from unknown-send without deadlocking. Check diagrams and the narrative use the same sequence.

### D05 — Rebase the delivery scope on two contributors and functional gates

**Evidence.** [First slice §3](../track2-first-vertical-slice.md) (baseline line 31) requires 31 core SQL tables, with 24 preceding the first integrated round trip and seven more before the full demo. [Its schedule](../track2-first-vertical-slice.md) (baseline line 44), [master ownership/schedule](../track2-final-architecture.md) (baseline line 456) and [delivery plan](../track2-delivery-and-validation.md) (baseline line 42) assume four people and four days. The combined release also includes 14 tools, two model roles, protected verification, two-store recovery, local authentication, private-source semantics, backup/restore, comparison, load probing and packaging. The latest user constraint is two full-time people and no newly specified deadline.

**Failure scenario.** Each table is treated as a repository/service/UI to finish, leaving no complete workflow. The team spends its integration budget on two model-role lifecycles, general approvals or onboarding before proving memory continuity. Cutting a few screens cannot compensate for unspecified work across capture, effects and two durable stores.

**Minimal resolution.** Keep the requested PostgreSQL + FalkorDB architecture and full target schema. Table count alone does not demonstrate overengineering, and creating reviewed tables is cheaper than implementing every associated behavior. Use a reviewed bootstrap migration or an explicitly FK-closed slice; implement only operations used by the current feature gate. Do not require 24 bespoke repositories before one model turn. Treat model-role concurrency, generalized private-context ingestion/publication, automatic summaries, native providers, remote endpoints and broad backup tooling as separate feature decisions. Refusing unsupported private ingestion is safer and smaller than pretending a declassification workflow exists; keep synthetic tenant/project/private-source denial tests.

The minimum product should have one live Builder, a fresh successor after confirmed retirement, deterministic protected verification, one fixture, one API route and one tested Docker/OS target. Keep typed capture, current requirements, source inspection, duplicate/stale guards and tested restart behavior. An incomplete gate is a smaller stated release, not an invented pass. Retain fault gates required by whatever durability is actually claimed.

**Acceptance experiment.** From an empty installation, complete one vertical trace through human source, graph authority, provider request, actual tool result, interruption, fresh recovery and trusted final receipt before adding unused repositories or UI. Maintain a feature-to-operation/table matrix. The release package must not require deferred adapter/auth tables or unimplemented feature callbacks merely to start. Estimate each next gate after the preceding trace exists; do not assert an unsupplied calendar deadline.

### D06 — Establish one ownership matrix

**Evidence.** [Master §18](../track2-final-architecture.md) (baseline line 460) assigns Engineer 2 TUI/fixtures/verification and DevOps 2 runtime/provider integration. [Delivery §4](../track2-delivery-and-validation.md) (baseline line 47) assigns Engineer 2 the owned model/tool loop and DevOps 2 provider integration plus isolation/packaging. Both assume four named roles.

**Failure scenario.** Provider normalization, durable tool barriers and fixture integration fall between owners, or both people implement competing loop seams. With only two contributors, documentation that names four roles obscures workload rather than distributing it.

**Minimal resolution.** One person owns runtime/provider/tool contracts, local service and minimal TUI. The other owns graph authority/context, SQL/capture integration, fixture verification and packaging. Adjust that split to actual strengths, but explicitly name one owner of shared contracts, admission, artifact identity and the first end-to-end trace. Both review cross-store/effect boundaries. Reference this matrix from other documents instead of maintaining competing copies. Shared work is not ownerless work.

**Acceptance experiment.** For every first-gate operation, identify its implementing owner, caller, stable input/output schema and one failure fixture. Neither person needs to infer who implements the boundary from a broad job title.

### D07 — Specify one executable verification and containment profile

**Evidence.** [Runtime §16](../track2-runtime-and-protocols.md) (baseline line 240) correctly protects the acceptance bundle and places assertions/receipt writing outside candidate-controlled execution. [Delivery topology](../track2-delivery-and-validation.md) (baseline line 32) selects restricted containers, with Linux containers on one macOS/Docker reference host at [line 38](../track2-delivery-and-validation.md) (baseline line 38). [Tool execution](../track2-runtime-and-protocols.md) (baseline line 119) requires timeouts, process containment and confirmed termination. These are sound requirements, but the actual authored-program interface, protected launcher protocol, mounts, network mode and completion evidence are not yet fixed.

**Failure scenario.** One implementation runs tests by importing candidate code into the same Node process that holds assertion functions; another uses a subprocess but lets the candidate control a package script or mounted helper. Both can appear to satisfy “separate Verifier” while failing the intended trust boundary. A shell process terminating does not by itself prove descendants or the container are gone.

**Minimal resolution.** Select one JSON request/response fixture protocol. A protected supervisor runs the candidate in a restricted process/container, validates bounded output as untrusted data, performs assertions itself and creates the receipt. Choose concrete readonly candidate/protected-check mounts, writable scratch, network denial, resource limits and stable execution identity. Use container lifecycle evidence to reconcile termination. Restrict the MVP to this supported program shape; do not claim a generic sandbox or general test-framework isolation. This technical choice should precede affected executable-tool implementation, and the proof should precede support claims; it need not prevent unrelated documentation or scaffolding work.

**Acceptance experiment.** In a short isolated spike, run an incorrect candidate, a candidate printing forged success, an early-zero-exit candidate, a background child, an attempted host-path escape and an attempted secret/network access. The trusted check fails or containment denies as specified, and timeout does not release the write scope until termination is established. A correct candidate produces a receipt tied to the exact protected bundle and candidate bytes.

### D08 — Turn bounds and cadence into a usable policy

**Evidence.** [Runtime §20.5](../track2-runtime-and-protocols.md) (baseline line 342) specifies a 6,000-token default/8,000-token maximum memory packet but leaves total request limits to configuration. [Streaming capture](../track2-runtime-and-protocols.md) (baseline line 366) leaves batching/crash-loss parameters to the release manifest. [Checkpoint timer](../track2-runtime-and-protocols.md) (baseline line 377) is intentionally untested and unspecified. [Availability policy](../track2-final-architecture.md) (baseline line 242) promises a bounded fsynced spool without a selected size/exhaustion profile. [Retention](../track2-data-model.md) (baseline line 137) leaves exact defaults for later measurement.

**Failure scenario.** Implementers choose incompatible defaults, a poll waits longer than a command's remaining deadline, or unknown model attempts retain reservations until every future attempt is blocked with no user-visible recovery policy. A memory packet can fit while total provider input or accumulated tool output exceeds its budget. “Bounded” cannot be acceptance-tested without a concrete bound.

**Minimal resolution.** Freeze one versioned fixture policy before the first paid run: input/output/headroom limits, model turns, tool actions, command deadline/yield/poll limits, per-call/cumulative output, capture batch sizes, spool quota, queue/outbox batch sizes, leases/retries, and retained-evidence policy. Initial values are adjustable hypotheses, not tested capacities. For the first fixture, deterministic checkpoint triggers on terminal failure, candidate creation and explicit pause are enough; a timer is not required to create correctness. Never wait for a model checkpoint on urgent cancellation.

**Acceptance experiment.** Boundary-test each selected limit at the threshold and one unit beyond it. Confirm a terminal outcome cannot be discarded because the output budget filled, routine reads add no summarization calls, all unknown statuses remain inspectable, and default recovery succeeds with optional condensation disabled. Report actual observed costs and tune only from measurements.

### D09 — Define how relevant memories are found before they are linked

**Evidence.** [Context selection](../track2-final-architecture.md) (baseline line 313) starts from a task and traverses relevant source/artifact relationships, applying requirement/artifact/environment applicability before optional ranking. [Runtime §20.2](../track2-runtime-and-protocols.md) (baseline line 297) lists deterministic relevance/applicability/novelty/size but no concrete seed or comparison predicate. The graph relationships at [lines 700–702](../schema/graph-field-dictionary.md) (baseline line 700) connect Procedure to its validation receipt and required constraint version, and Attempt to a procedure it already used. The definitions are sufficient for inspecting a known procedure, but do not select how a new task discovers one before reuse.

**Failure scenario.** A held-out task has no `USES_PROCEDURE` edge yet, so task-only traversal finds nothing. Alternatively, broad project scanning returns unrelated lessons. Exact candidate/global-requirement equality is appropriate for a completion receipt but would exclude an older failed attempt precisely when a changed candidate needs advice; weakening all equality checks would wrongly make old proof current.

**Minimal resolution.** Choose an explicit bounded bootstrap: a fixture task-family/command/criterion key selects a small authorized project-level procedure/episode candidate set, then graph relationships retrieve source and validation evidence. No vector index is required. Define separate predicates: current proof requires exact candidate/criteria/environment/current-authority bindings; advisory recall requires declared compatible task family, relevant unchanged obligation/environment and visible source, and is labelled historical/conditional. A failure from candidate A can inform work on candidate B without proving B fails or passes. Provide an explicit incompatible/unknown result rather than guessing relevance. P0 closure remains exact and independent of optional ranking.

**Acceptance experiment.** Seed one applicable procedure, a superficially similar incompatible one and an obsolete failure. Create a new task with no prior usage edges. Retrieve the applicable conditional record using the declared key, explain the selection path, and exclude/label the others correctly. Change an unrelated global requirement and then a relevant obligation: the first must not blindly erase useful advice, while the second must invalidate incompatible applicability. Neither case revives an old verification receipt as current proof.

### D10 — Require a reason for a second model, not merely a second role label

**Evidence.** [First slice](../track2-first-vertical-slice.md) (baseline line 19) commits to two live role workers. [Verifier assignment](../track2-runtime-and-protocols.md) (baseline line 236) scopes the Verifier to exact candidate/criteria checks. [Trusted acceptance](../track2-runtime-and-protocols.md) (baseline line 242) and [completion](../track2-final-architecture.md) (baseline line 352) are already determined by protected service logic and current executable evidence.

**Failure scenario.** A second model adds provider calls, context, usage reservations, session recovery and additional integration work simply to invoke a known check list. Its confident review is then confused with the actual independent evidence. This is a product/scope concern, not a claim that model reviewers are useless.

**Minimal resolution.** For the two-person MVP, use a deterministic protected verifier service and one live coding model. Demonstrate cooperation across old and genuinely fresh Builder sessions plus protocol concurrency, labelled honestly. Do not advertise two simultaneously reasoning agents. Keep a future model Verifier role in the target architecture only if it has a concrete additional task, such as selecting a declared diagnostic probe or producing a sourced review finding, and its benefit justifies the cost. A model review can supplement but never replace trusted checks.

**Acceptance experiment.** Complete the core recovery trace with no second model call. If a later reviewer is added, compare the same acceptance bundle and overall budget with and without that role, measuring extra defects found, false claims, latency and cost. Retain it based on observed value rather than the desired architecture diagram.

## 3. Smallest honest MVP

The proposed minimum retains the selected TypeScript/Node, PostgreSQL, FalkorDB and immutable artifacts. It has one local authenticated user workflow, synthetic scope-denial tests, one API profile, one authored workspace and one live Builder. The user can start the accepted fixture, inspect a real failed attempt, change its accepted requirement, stop the worker and continue in a genuinely fresh session. A deterministic verifier checks the exact final candidate. The result is a reviewable patch plus inspectable current authority, source-linked observations and trusted receipts.

Its memory capability is deliberately concrete: exact accepted requirements; deterministic execution episodes; one structured checkpoint/checklist with capture coverage; one sourced procedure template with explicit compatible trial and held-out validation; bounded deterministic retrieval. It uses no extra model to summarize or create semantic authority. The ordinary model/tool loop is enough.

The first implementation gate should use only the tools needed to cross the seam—read/inspect, patch, a registered check and checkpoint/context delivery. A larger registry can remain a target while clarification, checklists and asynchronous polling are added only when their durable contracts are exercised. Tool count is not the value proposition. The exact public release registry must reflect what passes, not everything listed in the architecture.

Keep the full schema as a reviewed compatibility target; a bootstrap migration can create more tables than the MVP actively uses. Do not add generic repositories/screens just because a table exists. Do not replace the requested two-store design silently. If time forces a different storage product, that is an explicit redesign and a smaller claim.

A practical gate order for two contributors is:

1. Freeze fixture, accepted command/check schemas, policy defaults and ownership; prove one guarded graph transition and the protected check protocol.
2. Run one actual model/tool round trip with SQL capture, graph provenance and inspectable source bytes.
3. Interrupt after a failed result, change authority, replace the worker and recover the exact checkpoint plus tail with summarization disabled.
4. Finish the correct candidate, reject stale proof, perform held-out procedure reuse and compare with an equally informed structured-checkpoint baseline.
5. Package and run restart, duplicate/stale, source denial and bounded protocol concurrency tests. State every remaining limitation.

No numerical schedule is promised by this report. Estimate the next gate using actual completion of the preceding integration trace and the two contributors' skills.

## 4. Decisions that should remain settled

- TypeScript is a reasonable application language for this I/O-heavy tool/runtime boundary. Rust is not required for a small loop; the difficult work is protocol and isolation correctness.
- Owning a bounded loop is consistent with the user's harness goal. Codex/Pi archives are useful references; a full fork or new orchestration framework is unnecessary for the selected workload.
- Durable capture, semantic acceptance, forwarding priority and retention are different operations. Runtime sections 20–21 express this well. The critique asks for operational mappings rather than a paid summary after every turn.
- Mandatory current authority must not compete in top-k recall. Exact proof and conditional advice need different applicability predicates.
- One official API route is the smallest first authentication scope. Native subscriptions and direct provider OAuth remain later routes, not impossible routes. No credential-cache extraction or new provider-policy claim is needed to solve this review.
- PostgreSQL and FalkorDB have explicitly separate authority. Outboxes, command/model intent journals, epoch checks, privacy ordering and trusted receipts are meaningful corrections already present; they should not be removed to make the diagram smaller.
- A proposal clearly labelled unexecuted is not a false benchmark. Static schema/diagram checks are useful but do not replace database, containment or recovery experiments.
