# Independent evaluation of Threadline development readiness

**Review date: 15 October 2026. Status: independent design review; product execution remains untested.** This is a fresh review of the current plans, separate from the [earlier architecture evaluation](track2-critic-evaluation.md). It evaluates whether two full-time developers can begin a specific, coherent implementation without inventing important missing contracts. No delivery deadline was supplied; a previous four-day suggestion is not a user commitment.

**Final design verdict:** the revised controlling blueprint is ready to start its contract/containment preflight and first vertical implementation. D01–D10 have adequate design dispositions for the selected one-model, authored-fixture scope. This does not certify a working harness, safe sandbox, passing migration or demonstrated memory benefit.

The evaluator inspected the current architecture, runtime protocols, delivery cut, storage dictionaries and diagrams independently before coordinating finding IDs with the critic. The parent agent owns changes outside this report. Findings concern missing or conflicting design contracts, not alleged failures of nonexistent application code.

## 1. Development decision

The smallest useful first release is an owned TypeScript harness with one model-driven Builder, durable captured observations, accepted current requirements in FalkorDB, a fresh replacement Builder, and a trusted deterministic verification service. The product outcome is that the replacement continues the correct current work with relevant evidence after an interruption. It must not rely on the old conversation or a final model-written recap.

This demonstrates coordination between successive sessions and shared persistent task state. It does not demonstrate concurrent model-agent teamwork. A second model reviewer should remain a later capability unless its distinct review job is worth the additional scheduling, policy and evaluation work. Protected executable assertions already decide the fixture's objective completion; calling the same checks through another model does not independently strengthen them.

Retain TypeScript/Node, the local TUI, PostgreSQL for identity and durable operational/source records, FalkorDB for memory and task authority, and immutable local artifacts. Replacing this selected two-store design would reopen a larger architecture decision. Instead, make its cost visible and implement one reviewed bootstrap migration plus the workflow-specific queries actually needed. Thirty-one core tables do not imply thirty-one custom repository layers or UI screens, and table count alone proves neither simplicity nor excessive scope.

Use one backend process with logical model sessions. The supervisor separately manages actual command/container processes with stable invocation identities. Pin one provider, one reference operating environment, one authored workload and one protected check protocol. Additional providers, native subscription adapters, distributed coordinators and generalized spawning do not block this first outcome. The removed recursive-analysis module has no place in the active design or build prerequisites.

## 2. What the current memory design gets right

Runtime sections 20 and 21 distinguish captured originals, accepted authority, derived recollections, forwarded context and retention. These are different operations, and their separation addresses the user's concern about memory priority and summarization cadence.

The four priority bands are a sensible first implementation: exact mandatory authority and unresolved effects first; active checkpoint/blocker/evidence next; compatible historical lessons and procedures after that; bulk trace last. Apply permissions and applicability before ranking. A useful failure is an episode with a command, outcome, candidate/environment and source, not merely a short error sentence or a list of touched files.

Capture at durability boundaries, checkpoint at meaningful changes, and recover from a checkpoint plus later captured events. Deterministic templates and ordinary agent checkpoint tools are enough initially. A separate summarization model or service is unnecessary. Model condensation remains optional and disabled; a crash or cancellation must never wait for it. Memory-packet limits and the full provider-request limit must both be enforced, since bounding only the recalled memory leaves tool schemas and recent history unbounded.

These are good proposed policies. Their implementation still needs exact checkpoint provenance, a bounded recovery-tail algorithm, procedure discovery and numerical startup defaults. Calling these gaps out does not invalidate the overall memory design.

The provisional assessment had reserved judgment on D05 and D07; the finalized report explicitly avoids the stronger interpretations this evaluator challenged. D10 remains a worthwhile scope choice rather than a demonstrated logical defect in a two-model design.

## 4. Future acceptance criteria

These checks are proposed and unexecuted. They should become executable tests or recorded probes against a versioned implementation, not additional prose assertions.

| Finding | Observable acceptance criterion |
|---|---|
| D01 | A clean bootstrap yields the fixture's exact accepted goal/constraint/criteria versions. The protected suite distinguishes the documented old and new requirement behavior on fixed cases; changing candidate-owned test scripts cannot redefine expected success. |
| D02 | Terminate the Builder after a captured failed command but before any voluntary checkpoint. A fresh request contains the current requirements, exact checkpoint/checklist source if any, the relevant failed episode and all unresolved effects. Long successful-read tails remain bounded without losing mandatory recovery facts. |
| D03 | A real successful receipt creates a traceable candidate procedure. One distinct compatible held-out task records actual reuse and promotes it only under the declared rule. A fabricated model success message, incompatible environment, or repeated receipt from the same task cannot promote it. |
| D04 | Crash before claim, after claim, before provider dispatch and after an ambiguous dispatch. Recovery yields one authorized successor, no provider call before authorization and no blind replay of uncertain provider/tool effects. |
| D05 | From clean databases, the first increment performs one durable goal → graph authority → persisted provider attempt → permitted captured observation round trip without implementing unused feature screens or a second model. Later increments preserve that path while adding continuity and checks. |
| D06 | The same two ownership lanes and shared contracts appear in the controlling implementation guide and delivery plan; neither requires a third implementer or an unstated deadline. |
| D07 | On the declared reference machine, an authored candidate attempts fixture/assertion tampering, prohibited file/network access, fake check output, premature success and resource exhaustion. Trusted assertion/receipt processes remain outside candidate control, and uncertain termination blocks conflicting access. Record actual limitations rather than infer complete containment from flags. |
| D08 | Tests using a controlled clock and bounded fake provider/command hit each configured limit, exercise lease expiry and log pressure, and verify a safe stopped/pending/unknown state. One real supported-model request confirms the configured input/output compatibility; defaults are not called performance results. |
| D09 | An authorized new task with no existing procedure edge discovers a compatible candidate/validated procedure through the declared seed. Wrong-family/private/incompatible items are excluded. An old receipt never proves a changed candidate, while an applicable failed strategy can still appear as historical advice. |
| D10 | The documented first-release trace uses one live model slot, terminates or quarantines it before successor write access, and obtains objective completion from the trusted service. Usage accounting contains no fictitious second-model calls. |

## 5. Remediation reread

The evaluator reread the [controlling development blueprint](../track2-development-blueprint.md), all four contract files, [domain vocabulary](../../../CONTEXT.md), changed graph fields/relationships and rebased [first vertical slice](../track2-first-vertical-slice.md). Contract inputs are the [fixture](../contracts/fixture-manifest.json), [development profile](../contracts/development-profile.json), [checkpoint schema](../contracts/memory-checkpoint.schema.json) and [episode schema](../contracts/memory-episode.schema.json). The two new [MVP architecture](../diagrams/development-mvp.mmd) and [checkpoint recovery](../diagrams/checkpoint-recovery.mmd) diagrams were also read for semantic agreement. Full HTML/rendering/static validation remains the parent agent's separate task, not an evaluator execution claim.

The controlling design now specifies one live Builder, a fresh successor and a deterministic checker, with eleven model-visible tools and three deferred target tools. It explicitly distinguishes logical in-process model sessions from real isolated command processes. The two contributor responsibilities, lack of a supplied deadline, bootstrap-schema strategy and seven functional build gates are concrete. D05, D06 and the recommended D10 scope decision are resolved in design.

The fixture defines exact CSV results, UTC normalization, initial/changed freshness values, error examples and compatible held-out input. The deliberate seed defect is disclosed. The plan correctly admits that a generic repaired implementation may satisfy the new threshold without another edit; the old receipt must still be replaced with current evidence. Authenticated fixture acceptance and normalized human changes supply authority. D01 is resolved as an implementation input, with creation/hashing of the seed and protected bundle explicitly left to the first gate.

The checkpoint schema contains per-session covered positions, source IDs, candidate/revision bindings, tactical steps, unresolved effects and a pending question. TaskState has an exact checkpoint Source pointer and `CHECKPOINT_SOURCE` relation. Deterministic terminal-event ingestion and bounded tail reconciliation now work as specified even when the model never voluntarily summarizes. The four-stream checkpoint bound matches one initial session plus three permitted replacements. D02 is resolved in design; semantic invariants such as unique session positions, coverage never beyond admitted capture, and preserving unrelated fields during checklist patches must be implemented and tested, since JSON Schema alone does not establish them.

The procedure path now starts from actual protected success, uses a disclosed authored template, permits an explicitly authorized compatible candidate trial, and validates only from a distinct held-out task/run receipt. `ProjectRoot-HAS_PROCEDURE` supplies the missing discovery seed. Exact proof and conditional advice have separate applicability rules. Proposed agent preferences do not silently become semantic authority. D03 and D09 are resolved in design. D04 is also corrected: stage locally, acquire the successor claim, rebuild against post-claim authority, then persist and dispatch the provider attempt.

The graph receipt now binds `check_run_id` and `verified_by_actor_id`, with `CHECKED_BY -> ActorRef`; `verifier_session_id` is optional for later model review. This avoids fabricating a second AI participant. The four JSON files select many useful numerical limits and explicitly mark their values unmeasured.

**Residuals found on the first remediation reread and subsequently corrected:**

- **D07/D08 — closed in design:** the profile now selects one CPU, 512 MiB memory, 64 PIDs, UID/GID 10001, read-only root/candidate, bounded scratch, no network/capabilities/privilege escalation/host socket, filtered environment and two-second stop grace. It supplies 30-second claim/outbox leases, ten-second claim heartbeat, 250 ms outbox polling and explicit replay-safe backoff. Expiry revokes admission but does not prove process termination; uncertain stops remain quarantined. These are concrete starting settings, not demonstrated containment or capacity.
- **P0 exactness — closed in design:** section 7 now permits only deduplication or compact encoding that preserves exact governing obligations. Persistent overflow blocks admission or requires explicitly accepted narrower scope/model-compatible budget. It no longer offers optional-history condensation as a way around mandatory authority.
- **Source inspection — closed in design:** `memory.retrieve` now has `mode=source` with source ID, byte offset and at most 32 KiB. Each range rechecks source availability/scope and session grants; output includes identity, digest, size and truncation. Raw artifact paths are unavailable. The existing tool supplies the required evidence drill-down without expanding the tool count.

The final reread also confirms explicit validation of unique per-session coverage, covered cursor not exceeding graph admission, and the four-stream bound. The new recovery diagram orders the successor claim before request submission. No remaining contradiction identified in these controlling contracts requires reopening the stack or adding another architecture layer.

Remaining implementation prerequisites are deliberately visible: exact compatible Node/container/model versions, lockfile, effective model limits, authored seed implementation, executable protected bundle, typed tool validators, migrations, actual containment probes and recorded integration outcomes. Fixture grammar/error edge cases must be fixed in its executable bundle before expanding accepted inputs. The lack of these artifacts is not a hidden design pass; it is the work of the first gate. Runtime, migration, provider, sandbox, recovery, privacy and evaluation gates remain unexecuted after written resolution.

## 6. Development gates versus release claims

The revised blueprint selects the fixture, process topology, authority/event boundaries, recovery provenance, resource defaults and increment order sufficiently to start gate 1. Unknown provider credentials or an unexecuted Docker probe do not prevent writing pure domain logic, capture contracts, database migrations or tests. They do prevent claiming the affected integration works.

Stop the affected release claim if durable command admission, source capture, current-authority selection, successor exclusivity, unknown-effect reconciliation, private-source filtering or protected verification fails. These are central product properties, not optional polish. Record each executed case, versions, actual outcomes and limitations.

Optional second-model review, broad spawning, additional providers, native subscriptions, large-scale load measurements, model summarization and polished navigation should not block the first honest demonstration. A small authored comparison against an equivalently informed structured checkpoint can show what the graph supplied; it cannot establish general intelligence or statistically reliable performance gains.
